이번 세션을 마무리하고 **다른 PC에서 그대로 이어받을 수 있는 상태**로 만든다.

사용자 메모: $ARGUMENTS

아래를 순서대로 하고, 각 단계 결과를 짧게 보고할 것.

## 1. 무엇이 바뀌었는지 파악

```
git status --short
git log --oneline origin/main..HEAD
git diff --stat
```

미커밋 변경과 미푸시 커밋을 모두 확인한다. 이번 세션의 대화 맥락도 함께 쓴다 —
git diff에 안 드러나는 **결정과 그 이유**가 인수인계의 핵심이다.

## 2. 검증 (코드가 바뀐 경우에만)

바뀐 영역에 해당하는 것만 돌린다. 실패하면 **거기서 멈추고 사용자에게 보고**한다 —
깨진 상태를 다른 PC로 넘기지 않는다.

- 프론트엔드/TS: `npx tsc --noEmit` 그리고 `npx jest`
- 백엔드: `cd backend && python -m unittest discover -p "test_*.py"`
- 문서만 바뀌었으면 생략

## 3. `docs/STATE.md` 갱신

**이것이 이 명령어의 핵심이다.** 다른 PC의 Claude는 이 파일 하나로 상황을 파악한다.
로컬 메모리는 PC를 넘어가지 않는다는 것을 기억할 것. 아래 틀을 유지한다:

- **마지막 갱신**: 날짜와 작업한 PC 구분.
  커밋 해시는 적지 말 것 — 이 파일을 커밋하는 순간 값이 바뀌어 항상 어긋난다.
  시점이 필요하면 다른 PC에서 `git log -1 -- docs/STATE.md`로 확인하면 된다.
- **지금 상태**: 무엇이 완료됐고 무엇이 대기 중인지. 외부 시스템 상태(Play Console
  심사 중 등)도 포함 — 저장소만 봐서는 알 수 없는 것들이다.
- **다음에 할 일**: 우선순위 순. 각 항목에 "왜 필요한지"와 "어디부터 손대면 되는지"
- **진행 중이던 작업**: 중간에 끊긴 게 있으면 어디까지 했고 다음 수가 무엇인지
- **최근에 알게 된 것**: 이번 세션에서 발견한 함정·원인·해결책. 다음 사람이
  같은 삽질을 반복하지 않도록. 오래 유효할 내용이면 `CLAUDE.md`나
  해당 주제 문서(`docs/release/play-console-checklist.md` 등)에도 반영한다.

추측을 사실처럼 쓰지 말 것. 확인 안 된 건 "미확인"이라고 적는다.

## 4. `todo.md` 갱신

완료한 항목은 `[x]`로 바꾸고 **무엇을 어떻게 검증했는지**를 남긴다.
새로 생긴 할 일은 추가한다.

## 5. 커밋 & 푸시

```
git add -A
git commit    # 한국어로, 왜 그렇게 했는지를 남긴다
git push origin main
```

민감정보가 섞이지 않았는지 확인한다 — `.env`, `*.jks`, `keystore.properties`는
gitignore 대상이지만 새 파일이 생겼다면 다시 본다.

## 6. 마무리 보고

사용자에게 이렇게 알린다:
- 이번에 푸시한 커밋 목록 (한 줄씩)
- 다른 PC에서 이어받는 방법: **`git pull` 후 `/resume`**
- 다음 세션이 시작할 지점 한 줄
