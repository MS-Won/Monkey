# 해몽 카테고리 개편 — 설계

작성 2026-07-26 · 출시 전 마지막 기능 변경

## 1. 배경

현재 해몽 한 번에 GPT를 **7회** 부른다. 꿈을 문장 단위로 쪼갠 뒤(`/split` 1회), 문장마다
해몽하고(`/interpret` N회, 순차 for 루프), 마지막에 종합한다(`/summary` 1회).

실측(2026-07-26, 프로덕션):

| 단계 | 호출 | 입력 토큰 | 출력 토큰 |
|---|---|---|---|
| `/split` | 1 | ~250 | ~100 |
| `/interpret` | 5 | 4,325 | 945 |
| `/summary` | 1 | ~1,200 | ~400 |
| 합계 | **7** | ~5,800 | ~1,350 |

비용 약 **$0.0017**, 지연은 7왕복.

`/interpret` 한 문장 호출의 입력이 865토큰인데 **문장 자체는 20토큰 남짓**이다. 나머지는
`PERSONA_SYSTEM`(말투 규칙 9개)과 전통 해몽 근거 블록이며, 이것이 문장마다 통째로
재전송된다. 문장이 늘어날수록 같은 프롬프트를 반복해서 돈과 시간을 쓴다.

동시에 UX 문제가 있다. 문장별 "풀이 해몽" 카드가 아르누보 카드보다 위에 렌더되어,
"카드를 먼저 보고 탭하면 해몽이 열린다"는 원래 연출이 묻혔다. 플립 코드 자체는 정상이다.

## 2. 목표

1. GPT 호출을 **7회 → 1회**로 줄인다. 비용 목표 ~$0.0006(약 1/3), 지연 1왕복.
2. 해몽을 문장별 나열에서 **의미 카테고리**로 바꾼다.
3. 카드를 먼저 보여주고 탭하면 해몽이 열리는 연출을 복구한다.
4. 프로필(나이대·직업)을 **기기 밖으로 내보내지 않고** 해몽 표시에 반영한다.

### 비목표

- 프로필을 서버로 전송하는 진짜 맞춤 해몽. 개인정보처리방침 수정과 Play 데이터 보안
  재신고가 필요하므로 별건으로 다룬다.
- 구 엔드포인트 삭제(`/split`, `/interpret`, `/summary`, `/embed`). 새 흐름이 실기
  검증된 뒤 다음 정리에서 한다.
- 스토어 스크린샷 재캡처. 해몽 화면이 바뀌므로 `screenshot-6-interpretation.png`은 결국
  갱신 대상이지만, 출시 직전에 한 번에 처리한다.

## 3. 백엔드 — 신규 엔드포인트 `/reading`

### 요청

```json
{ "text": "<꿈 전문>" }
```

프로필은 받지 않는다. 기기 밖으로 나가는 것은 꿈 텍스트뿐이며, 이는 현행
`docs/legal/privacy-policy.md`와 Play 데이터 보안 신고(`앱 활동 > 기타 사용자 제작 콘텐츠`
단독)를 그대로 유지한다.

### 처리

1. 꿈 전문에 `dream_lexicon.match_symbols()`를 **1회** 적용해 전통 해몽 근거 블록을 만든다.
   기존 `/interpret`은 문장마다 이 작업을 했다.
2. `PERSONA_SYSTEM` + 근거 블록 + 카테고리 지시로 GPT를 **1회** 호출한다.
3. 응답을 검증한 뒤 반환한다.

### 응답 스키마

OpenAI JSON 모드(`response_format={"type":"json_object"}`)로 받는다. 형식 위반이
구조적으로 불가능해지고, 프론트의 마크다운 헤더 파싱을 없앨 수 있다.

모델에게 받는 부분:

```json
{
  "summary": "종합 해몽 본문",
  "oneLine": "오늘의 한마디",
  "categories": [
    { "key": "work",   "body": "..." },
    { "key": "wealth", "body": "..." }
  ]
}
```

서버가 여기에 덧붙여 최종 응답을 만든다:

- `symbols` — `dream_lexicon.matched_headwords()` 결과. **모델에게 묻지 않는다.**
  사전 매칭은 결정적이고 무료이므로 모델이 상징을 다시 나열하게 할 이유가 없다.
  기존 `/interpret`도 `matchedSymbols`를 같은 방식으로 반환한다.
- `inputToken` / `outputToken` / `totalCostUsd` — `openai_chat()`이 돌려주는 값.

`key`는 고정 enum 6종이다.

| key | 표시 제목 |
|---|---|
| `luck` | 행운 |
| `caution` | 주의운 |
| `relationship` | 인간관계 |
| `wealth` | 재물운 |
| `work` | 직장·학업운 |
| `health` | 건강운 |

**제목 문자열은 프론트가 붙인다.** 모델이 매번 제목을 생성하면 토큰이 낭비되고 표기가
흔들린다.

**이모지는 쓰지 않는다.** 전통 해몽·아르누보 톤에서 이모지는 진정성을 떨어뜨린다.
제목은 한글 텍스트만 사용한다.

### 카테고리 선택 규칙

`summary`와 `oneLine`은 항상 생성한다. 6종 운세 중에서는 **꿈에 실제 근거가 있는 것만
2~4개**를 고르게 한다. 프롬프트에 근거 없는 칸을 채우지 말라고 명시한다.

"2~4개"는 **프롬프트 지시값**이고, 검증에서 받아들이는 범위는 **0~4개**다. 근거가 거의
없는 짧은 꿈에서 모델이 1개만 내는 것은 옳은 동작이므로 실패로 보지 않는다.

### 길이 상한

카테고리 본문은 **2~3문장**으로 프롬프트에서 제한한다. 비용의 70%가 출력 토큰이므로
(입력 $0.00015 vs 출력 $0.00042) 여기가 가장 큰 레버다. `summary`는 기존 종합 해몽
분량을 유지하고, `oneLine`은 한 문장이다.

8칸을 항상 채우게 하면 "배를 봤다" 같은 짧은 꿈에서 모델이 없는 내용을 지어낸다.
출력 토큰도 늘고, 전통 해몽 사전으로 그라운딩한 취지와도 어긋난다.

### 서버 검증

응답 검증은 **GPT 호출과 분리된 순수 함수**로 구현한다(테스트 가능성).

- `key`가 enum에 없는 항목은 버린다
- 유효 카테고리가 4개를 넘으면 앞 4개만 남긴다
- 유효 카테고리가 2개 미만이면 **그대로 반환한다**(0~1개도 정상). 짧은 꿈에는 근거가
  적은 것이 옳으므로, 개수를 채우려고 다시 부르지 않는다
- `summary`가 비었으면 500과 함께 실패를 반환한다. 해몽 없이 화면을 그릴 수 없다
- `oneLine`이 비면 빈 문자열로 두고, 프론트가 해당 블록을 숨긴다

## 4. 프론트 — 화면 재구성

### 표시 순서 (`ResultScreen`)

```
당신의 꿈 (원문)
      ↓
아르누보 카드 — 앞면만
      ↓  탭
카드 뒷면: 종합 해몽 + 오늘의 한마디
그 아래:   카테고리 섹션 (0~4개)
```

- 문장별 "풀이 해몽" `Card`를 **삭제**한다. `results` / `userExplainBlocks` /
  `isSingleSentence` 관련 상태도 함께 정리한다.
- 카테고리 섹션은 `cardFlipped`가 참일 때만 렌더한다. 탭이 실제로 "열어보는" 동작이
  되어야 하고, 이것이 목표 3의 핵심이다.
- 카드 뒷면에 8개 블록을 다 넣지 않는다. 뒷면은 좁으므로 핵심(종합 해몽 + 한마디)만
  담고 세부 운세는 카드 아래에서 펼친다.

### 로컬 프로필 정렬

기기의 `ageGroup` / `jobGroup`으로 **카테고리 순서만** 조정한다. 서버로는 아무것도
보내지 않는다.

| 프로필 | 우선 노출 |
|---|---|
| 학생(`STUDENT`) 또는 10대(`TEENS`) | `work` |
| 직장인(`EMPLOYEE`) · 자영업(`SELF_EMPLOYED`) | `work`, `wealth` |
| 구직(`JOB_SEEKER`) | `work` |
| 은퇴(`RETIRED`) 또는 60대+(`SIXTY_PLUS`) | `health` |
| 전업(`HOMEMAKER`) | `relationship`, `health` |
| 미입력 | 백엔드 순서 유지 |

정렬은 안정 정렬로 구현한다. 우선 키가 아닌 항목의 상대 순서는 백엔드가 준 순서를
유지한다.

**직업과 나이대가 서로 다른 키를 가리키면 직업을 우선한다.** 예: 직업 `EMPLOYEE`(→`work`,
`wealth`) + 나이대 `SIXTY_PLUS`(→`health`)인 경우 최종 우선순위는 `work`, `wealth`,
`health` 순이다. 직업이 현재 생활을 더 직접적으로 반영하기 때문이다. 한쪽만 입력된
경우 입력된 쪽만 적용한다.

**한계를 명시한다.** 모델이 애초에 `work`를 내지 않았으면 올릴 것이 없다. 프로필을
보내지 않으므로 "10대 학생 맞춤 문구"가 생성되는 것이 아니라, 생성된 것 중 순서와
강조만 맞춰진다. 이것이 개인정보 상태를 유지하는 대가다.

**성별은 정렬에 쓰지 않는다.** 성별로 운세 비중을 바꿀 근거가 없고, 편견으로 읽힐
소지만 있다.

### 성별 필드 제거

- `ProfileScreen`: 성별 필드와 선택 시트를 제거한다. 온보딩 진행 조건을
  `이름 → 나이대 → 직업`으로 재배선한다. 현재 `showAge`가 `genderOk`에 걸려 있어
  성별만 지우면 나이대가 열리지 않는다.
- `profileContext.ts`: `Gender` 타입과 `buildProfileContextForPrompt`를 제거한다.
  후자는 프로필을 프롬프트에서 뺀 뒤로 이미 죽은 코드다.
- 기존에 저장된 `gender` 값은 그대로 둔다. 읽지 않으면 무해하며 마이그레이션이 필요없다.

### 저장 포맷

기존 `dream_diary.interpretation` 컬럼에 **렌더된 평문**으로 저장한다. 스키마를 바꾸지
않으므로 마이그레이션이 불필요하고, 과거 기록도 그대로 열린다.

형식은 다음으로 고정한다(빈 블록은 생략, 블록 사이 빈 줄 하나):

```
종합 해몽
<summary>

직장·학업운
<body>

재물운
<body>

오늘의 한마디
<oneLine>
```

카테고리 순서는 **정렬을 적용한 뒤의 순서**로 저장한다. 화면에서 본 것과 꿈기록에
남는 것이 같아야 한다.

`keyword`(카드 영문명)와 `luckyScore` 계산은 변경하지 않는다. `luckyScore`는 저장할
평문을 입력으로 받는다.

### 카드 선정

기존 `selectArchetypeCard(dreamText, ...)` 로직을 유지한다. 둘째 인자로 넘기던
문장별 해몽 합본이 없어지므로, `summary`와 모든 카테고리 `body`를 이어 붙여 넘긴다.
백엔드가 주는 `symbols`는 보조 신호로 쓴다.

### 캐시 제거

기존 임베딩 유사도 캐시를 **없앤다.** 문장마다 `/embed`를 부르고 SQLite `cache` 테이블을
전수 스캔해 코사인 유사도 ≥0.9면 GPT를 건너뛰던 구조다.

없애는 이유:

- **적중률이 무너진다.** 캐시 단위가 문장이었기에 "뱀을 봤다" 같은 짧은 장면이 재발하면
  맞았다. 새 설계의 단위는 꿈 전문이고, 꿈 전체가 90% 이상 똑같이 반복되는 일은 거의 없다.
- **꿈 단위 유사도 매칭은 위험하다.** 사용자가 다르게 쓴 꿈에 똑같은 해몽이 나오면
  앱의 신뢰가 깨진다. 문장 단위에서는 감수할 만했지만 전문 단위에서는 아니다.
- **`/embed` 왕복이 사라진다.** 문장마다 붙던 네트워크 왕복과 임베딩 비용이 없어진다.
- 캐시 조회가 JS에서 전체 행 스캔이라 기록이 쌓일수록 느려지던 문제도 함께 사라진다.

중복 제출(해몽하기 연타, 뒤로 갔다가 재실행)은 **버튼 비활성화**로 막는다. 요청 중에는
해몽 버튼과 음성 입력을 모두 비활성화한다. 이미 `isLoading`으로 그렇게 하고 있으므로
새로 만들 것은 없다.

정리 대상:

- `frontend/src/logic/AnalyzeSentence.ts` — 문장별 해몽 + 캐시 로직. 삭제한다.
- `frontend/src/logic/embedding.ts` — 사용처가 없어진다. 삭제한다.
- SQLite `cache` 테이블 — **그대로 둔다.** 읽고 쓰지 않으면 무해하고, 테이블을 지우는
  마이그레이션은 위험 대비 이득이 없다(과거에 트랜잭션 분리 문제로 테이블이 유실된 적이
  있다).
- 백엔드 `/embed` — 구 엔드포인트 3개와 함께 다음 정리에서 제거한다.

**서버 측 캐시는 선택지에서 제외한다.** 사용자 간 공유 캐시는 적중률이 오르지만 꿈
텍스트를 서버에 저장해야 하고, 이는 개인정보처리방침의 "서버 미저장"과 Play 데이터 보안
신고를 정면으로 위반한다.

**OpenAI 프롬프트 캐싱도 해당 없다.** 공식 문서상 최소 1,024토큰부터 적용되는데, 우리
정적 프롬프트(`PERSONA_SYSTEM` ~500 + 카테고리 지시 ~200 ≈ 700토큰)는 문턱 미달이다.
문턱을 넘기려고 프롬프트를 늘리는 것은 본말전도다.

### 로딩 문구

`/split`이 사라지면서 `InputScreen`의 로더도 없어진다. 남는 로딩 화면은 `ResultScreen`의
`CardCreationLoader` 하나뿐이므로, 여기 문구를 **"당신의 꿈을 풀이하고 있습니다"**로
바꾼다.

## 5. 데이터 흐름

```
InputScreen (텍스트 또는 음성)
      │  꿈 전문 · 요청 중 버튼 비활성화
      ▼
ResultScreen ── POST /reading ──► 백엔드
      │                            │ dream_lexicon 매칭 1회
      │                            │ GPT 1회 (JSON 모드)
      │◄── {summary, oneLine, categories, symbols} ──┘
      │
      ├─ selectArchetypeCard() → 카드 결정
      ├─ 로컬 프로필로 categories 정렬
      ├─ 렌더 평문 조립 → saveDreamDiary()
      ▼
카드 앞면 → 탭 → 뒷면 + 카테고리
```

네트워크 왕복은 **1회**다. 이전에는 `/split` 1 + (`/embed` + `/interpret`) × N + `/summary` 1
이었다.

## 6. 오류 처리

| 상황 | 처리 |
|---|---|
| 네트워크 실패 / 타임아웃 | 기존 방식대로 오류 Alert 후 뒤로 |
| `summary` 없음 (500) | 오류 Alert. 저장하지 않는다 |
| `categories`가 0개 | 종합 해몽 + 한마디만 표시. 정상 경로로 취급 |
| `oneLine` 없음 | 해당 블록만 숨김 |
| 알 수 없는 `key` | 서버에서 이미 제거됨. 프론트는 방어적으로 무시 |

## 7. 검증 계획

이 프로젝트에는 자동 테스트가 없다(jest 설정만 있고 테스트 파일 0개, 백엔드도 없음).
지금까지 `tsc` + 에뮬레이터 육안 검증으로 진행해 왔다.

**신규: 백엔드 계약 테스트.** 취약점이 응답 검증에 모여 있으므로 여기만 자동화한다.
검증 함수를 순수 함수로 분리하고 `python -m unittest`로 돌린다. GPT를 실제로 부르지
않으므로 빠르고 무료다.

- 유효 응답을 통과시킨다
- enum에 없는 `key`를 버린다
- 5개 이상이면 4개로 자른다
- 0~1개도 통과시킨다
- `summary`가 비면 실패로 판정한다

**수동 검증.**

- 백엔드: 짧은 꿈("배를 봤다")과 다사건 꿈(구렁이·물·할머니·금가락지) 양쪽으로 실제
  호출. 짧은 꿈에서 카테고리를 지어내지 않는지 확인
- 비용: 실제 토큰을 재서 목표(~$0.0006)와 대조. 현재 $0.0017
- 프론트: `tsc --noEmit` 0오류
- 에뮬: 카드 앞면 → 탭 → 뒷면+카테고리 등장 / 프로필별 순서 변화 / 성별 필드 사라짐 /
  온보딩 3단계 진행 / 꿈기록 저장·열람 / **과거 레코드가 그대로 열리는지**

## 8. 롤백

백엔드는 신규 엔드포인트 추가이고 구 엔드포인트 3개가 살아 있으므로, 프론트를 되돌리면
즉시 이전 동작으로 복귀한다. 프론트 변경은 커밋 단위로 나눠 되돌릴 수 있게 한다.

## 9. 결정 기록

| 저장은 렌더 평문 | 스키마 변경과 마이그레이션을 피하고 과거 기록 호환을 지킨다 |
